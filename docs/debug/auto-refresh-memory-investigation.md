# 自動更新中のメモリ増加調査

## 現状

2026-10-19時点の調査メモ。自動更新中にChromeタスクマネージャーのメモリが増え続けるという報告を受け、Chrome 155のリモートデバッグで対象スレッドを計測した。

**結論（原因特定済み・修正済み）:** ステータスバーが登録されたJSXをstateに保存していたことが原因。Preactは初回描画したJSX要素自体に親VNodeへの参照（`_parent`）を書き込むため、保存した要素がその時点のアプリ全体のVNodeツリーを保持し、そのツリー内のStatusBarが一つ前の要素を保持する連鎖ができていた。`StatusBarItem`がStatusBarの置き場へportalで描画する方式に変更した。詳細は末尾の「原因の特定」を参照。

## 観測結果

- 対象はChLensのスレッドページ。レス数は観測中に約889件から約950件へ増加していた。
- 約25秒の計測では、レス数が889件から892件へ増えた間にJSヒープが約82MBから約103MBへ増加した。短い区間の値であり、これだけではリークと一時割り当てを区別できない。
- 約1分の計測では、GC直後の約125MBから約290MBへ増加した一方、レス数は916件から921件、DOMノード数は約8,738から約8,773への増加だった。増分の差は大きいが、測定途中にHeapProfilerを使用しており、計測器の影響を完全には分離できていない。
- Chromeのタスクマネージャーでは対象拡張機能のメモリ約896MBが表示された。
- ユーザーが保存した `E:\Downloads\Heap-20261019T145104.heapsnapshot` は約2.68GB。ファイルをストリーム走査した結果、スナップショット内に約2,583万ノードがあった。
- DevToolsのSummary画面では約1,813万オブジェクト、約772MBと表示され、`Object`グループ約302万件のRetained sizeが約721MBだった。
- 同画面のRetainers経路はVNodeの`children`と配列をたどっていた。表示された経路のDistanceは約1,855だが、GCルートまたは所有コンポーネントまでの末端は未確認。
- 保存ファイルの集計では、`Object`約569万件、配列約297万件などが見つかった。Context scopeグループが複数あり、それぞれ約15.8万件のものがあった。これらは描画ツリーの蓄積を疑う材料だが、個数だけでリーク元を断定できない。

## コード上の確認

- `useAutoRefreshTimer`はintervalを作成し、effect cleanupで`clearInterval`する。単純なタイマー増殖は現時点で確認できていない。
- `ThreadService`は取得完了時に該当URLの`pendingRequests`を削除する。
- 表示用スレッドキャッシュはURLをキーに上書きするため、自動更新履歴を無制限に保存する実装ではない。
- 取得結果の整形では全レスの置換・正規化・NG評価を行い、`useThreadData`は全レス一覧を更新する。これは更新ごとの大きな一時割り当てを生み得るが、単独ではオブジェクトが残り続ける説明にならない。
- `ThreadPage`は`displayedResponses.map`で表示対象レスをすべて描画し、`ResItem`のkeyにはレス番号を使っている。仮想化は確認できていない。
- PreactのContext購読はコンポーネントのunmount時に購読を外す実装。コンポーネントが正しくunmountされるなら、Context購読そのものが永久に積み上がる設計ではない。

## 有力仮説

自動更新の再描画後も、以前のレス行またはVNodeツリーが何らかの参照から保持されている可能性が高い。Context scopeやレス行らしいクロージャの個数も多く、レス行コンポーネントの再マウント／保持状態を重点的に疑う。

ただし、現時点では次を区別できていない。

1. 古いレス行コンポーネントが更新ごとに残るリーク
2. Preact互換レンダラーやイベント／Context購読のライフサイクル不整合
3. スナップショット生成・プロファイラーによる計測オーバーヘッド
4. 長いスレッドを全件DOM描画することによる通常のメモリ負荷

## 未確認事項と次の確認

1. Heap SnapshotのRetainersをGCルートまでたどり、ルートを保持しているコンポーネント、配列、クロージャを特定する。
2. レス番号の重複がないか確認し、`key={res.num}`の衝突可能性を除外する。
3. 自動更新停止後にGCした状態と、更新を続けた状態のスナップショットを比較する。特にレス数が変わらない更新でも、レス行VNodeとContext scopeが世代ごとに増えるか確認する。
4. 既存タブを閉じる／別ページへ移動した後に、旧レス行コンポーネントが解放されるか比較する。
5. 比較時はHeapProfilerやHeap Snapshotの取得自体がメモリを大きく使うため、タスクマネージャーの値とJSヒープの値を分けて記録する。

ユーザーがコマンド実行を停止したため、それ以降の実行中ページへのコマンド送信は行っていない。現段階では仮説の報告に留め、原因を断定する修正はまだ行わない。

## 原因の特定

保存済みスナップショットをストリームで読み込み、GCルートからの最短経路を幅優先探索で計算した。

- Distance 100以上の位置に約712MBが残っていた。ResItem内のクロージャ（`onAnimationEnd`・`onUrlClick`・`onUrlContextMenu`）が各約15.4万個あり、レス約950件×約160世代分の描画結果に相当した。
- 最深経路（Distance 1,895）は16ステップ周期で同じ形を繰り返していた。`page-count-status`のdivの`props.children`が前の世代のbutton VNodeを指し、そのbuttonの`__`（`_parent`）が古いStatusBar、`paneBody`のFragment、その`props.children[12]`（古い`<StatusBar />`要素）へとつながり、さらに古いbuttonへ続いていた。
- 連鎖の条件は「ペイン（`PaneColumnInner`）の再描画で`<StatusBar />`要素が作り直されること」と「レス数表示のJSXが更新されてStatusBarだけが再描画されること」が交互に起きること。自動更新ではレス数が変わるたびにこれが起きる。
- memo化したレス行リストだけを繰り返し再描画する実験では、到達VNode数はレス数に比例するだけで世代ごとには増えなかった。レス行の実装やPreactのContext購読は原因ではなかった。

## 対応

- `StatusBarItem`は表示内容（JSX）をProviderへ渡さず、StatusBarが描画した置き場のdivへ`createPortal`で描画する（`src/view/browser/components/StatusBar.tsx`）。
- 単体テストは通常Reactで動くため、Preactへ差し替えて検査する`StatusBar.preact.test.tsx`を追加した。修正前は50回の更新で到達VNode数が394から3,364へ増えて失敗し、修正後は一定になる。
- JSXをストアやモジュール定数に長く保持すると、Preactでは同じ種類の保持が起き得る。経路の入口にもモジュール定数のアイコン要素（`icon`）があった。こちらがどれだけ保持しているかは未確認。新しく作るときは表示内容をデータで持つかportalで描画する。
