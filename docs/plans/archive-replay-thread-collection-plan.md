## 1. 目的と範囲

過去実況再生（`src/features/archive-replay/`）の読み込みは、いまは実況スレッドURLを1行ずつ手で貼る方式になっている。1番組の実況はスレが数本〜数十本に分かれるため、URLを探して貼る作業が一番の手間になっている。そこで、**番組名などの検索語と時間帯から関連スレを集めて一覧にし、人が確認してから一括で読み込む**「リプレイ準備」を作る。

- 候補には確度のラベル（検索語一致・続きの可能性）を付け、**機械は候補を出すだけで、最終確定は人が行う**。実況スレには「【実況】◯◯を見ないスレ」「ネタバレ部」のような紛れが必ず混ざるため、全自動にはしない。
- 入口は2つ用意する。どちらも同じダイアログに行き着く。
  - 操作窓からの検索: 検索語と日時を入れて集める。
  - **実況・スレ画面からの呼び出し**: Mainで開いているスレ（現行・過去ログのどちらでも）を種にして、リプレイ準備を開く（§6）。見終わった実況スレや、過去ログ検索で見つけた1本から、そのまま再生準備に入れるようにする。

### 範囲外

- CM区間の推定とスキップ。別計画 `archive-replay-cm-plan.md` で扱う。
- ブラウザ版。過去実況再生がTauri専用のため、それに合わせる。
- 人の確認を省いた全自動の取得。
- 供給元を持たない板の収集。段階0で確認できた供給元だけを対象にする。

## 2. 前提として確認した現状

- 操作窓 `ui/ArchiveReplayWindow.tsx` は複数URLの入力（1行1件）・開始時刻・再生時間・再生倍率を持ち、`createArchiveReplayTimeline` が複数スレの合成・重複除去・時刻順の整列を既に行う。収集の出口は「URL欄へ流し込む」だけでよい。
- 次スレ機能 `src/features/next-thread/domain/` に、流用できる判定がそろっている。
  - `title-similarity.ts`: 装飾（転載禁止表記など）を除いた文字2-gram Jaccard類似度（`calculateBaseTitleSimilarity`）。
  - `thread-sequence.ts`: `★n`・`Part.n` の連番抽出（全角の正規化込み、`extractThreadSequenceNumber`）。
  - これらは候補一覧を外から受け取る純粋関数で、検索の供給元には依存しない。
- 機能間の依存は `vite.config.ts` の `FEATURE_PUBLIC_MODULES` に載せた公開モジュールだけ import できる。`next-thread` の公開一覧に `domain/next-thread-search` などはあるが、`domain/title-similarity`・`domain/thread-sequence` はまだない。使うなら一覧へ追加する。
- 窓をまたぐ連携は `platform/archive-replay-events.ts` の `defineTauriEventChannel`（型ガードつきevent契約）に集めてある。`requestArchiveReplaySeek` が「窓を開いてから通知する」形の先例になる。
- 起動コマンドは `browser/register-archive-replay-commands.ts` で `ExtensionApi.addCommand` に登録し、`when: () => isTauriRuntime()` でTauri版に限定している。
- スレの取得は `container.thread.getThread(url)`。dat直リンク（`/{板}/dat/{キー}.dat`）は `chlib` の `PATTERNS.CH_DAT` で通常のスレとして扱われ、dat落ちしたスレもこの形式で開ける見込み（CM計画の段階0と共通の確認事項）。
- 5ch互換のスレキー（URL末尾の数字）は**スレが立った時刻のepoch秒**。日時の範囲はキーの数値範囲へそのまま変換できる。

## 3. 構成

候補判定は、React・プラットフォーム・供給元に依存しない純粋関数として作る。供給元ごとの差は「一覧の取得」だけに閉じ込める。

```
packages/chlib/
  （段階0の結果しだい）  過去ログ索引のURL組み立てとパーサー。既存のsubject・bbsmenuパーサーと同じ置き場
src/features/archive-replay/
  domain/
    thread-collection/
      types.ts                種スレ・一覧の項目・候補・確度・パラメータの型
      candidate-matching.ts   一覧 → 確度つき候補（検索語一致・続きの可能性・連鎖追跡）
      collection-window.ts    種スレや日時入力 → 収集する時間範囲（キー範囲）
      gap-detection.ts        選択済み候補のレス時刻 → 覆えていない時間帯（段階4）
  browser/
    use-thread-collection.ts  検索・候補・選択状態を持つフック。一覧の取得と候補判定をつなぐ
  ui/
    ReplayPreparationDialog.tsx  リプレイ準備ダイアログ
    ReplayPreparationDialog.css
  platform/
    archive-replay-events.ts  既存。種スレを渡す「準備要求」channelを追加する（§6）
```

### 依存の向き

- `thread-collection/` は、自分の中のファイルと `next-thread` の公開モジュールだけを import する。`FEATURE_PUBLIC_MODULES` の `next-thread` に `domain/title-similarity`・`domain/thread-sequence` を追加する（archive-replay → next-thread の一方向。逆向きの依存はない）。
- 一覧の取得（HTTP）はドメインに入れない。URLの組み立てとパーサーは `packages/chlib/` に置き（段階0で確定）、呼び出しは `use-thread-collection.ts` からプラットフォームのHTTP経由で行う。
- ほかの機能からは使わないので、`FEATURE_PUBLIC_MODULES` の `archive-replay` 側は変えない。

### 型（案）

```ts
/** 実況・スレ画面から渡される種スレ。 */
interface ThreadCollectionSeed {
  threadUrl: string;
  title: string;
  /** スレキーから求めた立った時刻（epoch秒）。 */
  createdAtSeconds: number;
}

/** 供給元から得る過去ログ一覧の1件。供給元の差はこの型までで吸収する。 */
interface ArchivedThreadListing {
  threadUrl: string;
  title: string;
  createdAtSeconds: number;
  responseCount?: number;
}

type ThreadCollectionMatchKind =
  | "seed" // 種スレそのもの
  | "search-match" // 検索語一致（要確認）
  | "sequence-follow"; // 続きの可能性（要確認）

interface ThreadCollectionCandidate {
  listing: ArchivedThreadListing;
  kind: ThreadCollectionMatchKind;
  /** 類似度や連番の進みから求めた0〜1。既定のチェック状態と並び順の補助に使う。 */
  score: number;
  reasons: readonly string[]; // "title-contains-query" | "similar-to-selected" | "sequence-next" ...
}

interface ThreadCollectionParams {
  /** 種スレの前に遡る秒数と、種スレの後に見る秒数（既定: 前30分・後3時間）。 */
  beforeSeconds: number;
  afterSeconds: number;
  /** 続きの可能性と判定する類似度の下限。 */
  followSimilarityThreshold: number;
  /** 既定でチェックを外すscoreの下限。 */
  defaultCheckedThreshold: number;
}
```

## 4. 収集の方式

1. **収集範囲を決める**（`collection-window.ts`）。種スレがあれば `createdAtSeconds` の前後（既定: 前30分〜後3時間）、なければ利用者の日時入力。範囲はキーの数値範囲に変換できるので、供給元に日時検索がなくても索引の列挙＋範囲での絞り込みで足りる。
2. **一覧を取得する**。供給元ごとの取得（§5）で、範囲内の `ArchivedThreadListing` を集める。
3. **候補を判定する**（`candidate-matching.ts`）。
   - 検索語一致: 正規化（NFKC・装飾除去）したタイトルが検索語を含む。種スレがある場合の既定の検索語は、種スレのタイトルから連番と装飾を除いたもの。
   - 続きの可能性: 検索語には一致しないが、既に選ばれている候補と `calculateBaseTitleSimilarity` が閾値以上で、時刻が範囲内のもの。`extractThreadSequenceNumber` で連番が進んでいればscoreを上げる。「★11くらい」のような揺れた連番は、番号の厳密一致ではなく類似度で拾う。
   - **連鎖追跡**: 候補が増えるたびに「続きの可能性」の判定をやり直し、芋づる式に伸ばす。検索結果に出なかった後半のスレ（`Part.5` など）を、この連鎖で見つける。候補が増えなくなるまで繰り返し、上限回数で打ち切る。
   - URLの正規化で重複を除き、立った時刻順に並べる。
4. **人が確定する**。ダイアログの一覧（§5のUI）でチェックを外し入れし、「この内容でレスを取得」でURL欄へ流し込む。

閾値と既定値は `ThreadCollectionParams` に集め、関数の中に数値を直接書かない。各段は `(入力, params) => 出力` にそろえ、`Date.now()` と乱数は使わない。

### リプレイ準備ダイアログ

```
┌─ リプレイ準備 ──────────────────────────────┐
│ 検索語 [半沢直樹        ] 日時 [2020-09-27 20:30]〜      │
│ 供給元 [エッヂ ▼]              [候補を集める]           │
│ ─────────────────────────────── │
│ ☑ 20:58 【まったり】…第十話 ★1   1002レス 種スレ        │
│ ☑ 21:01 【TBS】…第十話(終) ★2   1001レス 検索語一致（要確認）│
│ ☑ 21:26 【TBS】…★11くらい      1002レス 続きの可能性（要確認）│
│ ☐ 20:57 【実況】…を見ないスレ       6レス 検索語一致（要確認）│
│ ─────────────────────────────── │
│ 選択: 12件                     [この内容でレスを取得]    │
└─────────────────────────────────┘
```

- 一覧は立った時刻順。各行に時刻・タイトル・レス数・確度ラベルを出し、確度の根拠（`reasons`）は `title` に出す。
- 既定のチェックは、scoreが `defaultCheckedThreshold` 以上の候補だけ入れる。レス数が極端に少ないスレは入るが、紛れのスレをいちいち外す手間を減らすため、scoreの低いものは外しておく。
- 「この内容でレスを取得」で、選択した候補のURLを操作窓のURL欄へ流し込む。取得そのものは既存の読み込み処理に任せる。開始時刻の入力が空なら、最初の候補の立った時刻から分単位へ丸めた値を入れる。
- 見た目は操作窓のCSSに合わせ、色・余白・角丸・影は `tokens.css` と `themes.css` の `--sys-*` を使う。

## 6. 実況・スレ画面からの呼び出し（段階3）

Mainで開いているスレを種にして、リプレイ準備を開けるようにする。現行の実況スレ（見終わった直後）でも、過去ログ検索や履歴から開いた古いスレでも、同じ入口を使う。

- **コマンド**: `archive-replay.prepare-from-thread`（ラベル案: 「このスレから過去実況リプレイを準備」）を `register-archive-replay-commands.ts` に追加する。`when` は「Tauri版で、アクティブタブがスレのとき」。コマンドパレットのほか、スレのメニューに出すかは実画面を見て決める。
- **イベント**: `archive-replay-events.ts` に準備要求のchannelを追加する（Main → 過去実況窓）。`requestArchiveReplaySeek` と同じく、窓を開いてから通知する。

```ts
interface ArchiveReplayPrepareRequest {
  version: 1;
  seed: ThreadCollectionSeed; // threadUrl・title・createdAtSeconds
}
```

- 受け取った過去実況窓は、リプレイ準備ダイアログを種スレ入りで開く。検索語は種スレのタイトルから連番・装飾を除いた値、日時範囲は `collection-window.ts` の既定（前30分〜後3時間）を入れた状態にする。
- `createdAtSeconds` はスレキーから求める。キーがepoch秒の形式でないスレ（外部板など）では、1レス目の投稿時刻で代用し、それも取れなければ種なし（検索語だけ入った状態）で開く。どの代用をしたかはログに出す。
- 現行スレ（まだdat落ちしていない）が種でも、収集の対象は過去ログの索引と現行の両方を見る。放送直後はまだ索引に載っていないスレがあるため、現行スレ一覧（subject）も `ArchivedThreadListing` へ変換して混ぜる。

## 7. 穴の検出と追加提案（段階4）

選択した候補を取得したあと、タイムラインに覆えていない時間帯（例: ★7の終わりから★9の頭まで10分の空白）が残ることがある。

- `gap-detection.ts` で、選択済みスレの最初と最後のレス時刻から、一定秒数（既定: 120秒）を超える空白を出す。
- 空白があれば操作窓に「21:3x〜21:4x が空いています。候補を探し直す」のような提案を出し、押すとその時間帯に絞ってリプレイ準備を開き直す。自動では探し直さない。
- 番組の進行で実況が静かな時間帯もあるため、空白＝取りこぼしとは限らない。提案の文言は断定しない。

## 10. 未決事項・リスク

- **供給元の持続性**: 過去ログの鏡や索引は形式が変わったり止まったりする。供給元の差を `ArchivedThreadListing` への変換に閉じ込め、形式の不一致はログと画面に出して気づけるようにする。
- **取得の行儀**: 一覧の列挙で供給元へ連続アクセスする。板単位の索引は1〜数ページで済む見込みだが、段階0でページ数を確認し、必要なら間隔を空ける。
- **複数板にまたがる実況**: 同じ番組の実況が板をまたぐことがある（CM計画 §10 の複数スレの合算と同じ事情）。まず1板で作り、供給元の選択を複数にできるかは段階2の後で決める。
- **検索語の既定が外れる番組**: 種スレのタイトルが番組名を含まない（「さあ半沢直樹だ！」のような単発タイトルが種になった）場合、既定の検索語では集まらない。検索語は常に編集できるようにしておく。
- **紛れのスレの既定チェック**: scoreの閾値だけでは「見ないスレ」「ネタバレ部」を確実には外せない。段階2の実画面で、よくある紛れの傾向（レス数が少ない・否定語を含む）を見てから既定を調整する。
- **実況中の呼び出しの広がり**: 現行スレから呼び出せると、「毎週の番組の先週分を見る」のような使い方が出てくる。種スレの履歴やお気に入りとの連携は、この計画では扱わず、使われ方を見てから考える。
