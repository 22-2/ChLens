## 1. 目的と範囲

過去実況再生（`src/features/archive-replay/`）で、実況ログからCMらしい区間を推定する。再生位置がその区間に入ったら、操作窓に「CMをスキップ」のフローティングボタンを出して提案する。**確かめていない区間は自動ではスキップしない**。押すかどうかは利用者が決める。利用者が承認した区間だけは、入ったときに自動で飛ばす（§5.2）。

使い方として、次の2つを想定する。どちらも「実況の再生位置をCMの終わりまで進める」という同じ操作で足りる。

- 配信版（CMなし）の動画に合わせて見る場合: 動画にはCMがないので、実況の側だけCMの分を飛ばさないとずれていく。
- 録画（CMあり）を見て、録画の側でCMを飛ばした場合: 実況の側も同じだけ飛ばす。

配信版に合わせて見る場合は、**放送と配信版の長さの差がCMの合計**になる。また、見ながら同期を合わせ直すたびに、それまでに過ぎたCMの合計がわかる。この2つを推定の制約と検算に使う（§4.3）。

### 範囲外

- 確かめていない区間の自動スキップ。誤判定で本編のコメントを飛ばすと取り返しがつかないため、提案に留める。
- CM中だけ倍速で流す再生方式。§10 の今後の候補に残す。
- 映像・音声の解析、LLMへのログ送信。手元のログと利用者の入力だけで完結させる。1番組で数十万字になり、送るたびに費用と待ち時間がかかるため。
- ブラウザ版。過去実況再生がTauri専用のため、それに合わせる。
- 他クライアントの配布物の解析。公開されたスクリーンショットと作者の説明から考え方だけを参考にし（§12）、推定方式とUIはこの計画の中で一から設計する。

## 2. 前提として確認した現状

- 操作窓 `ui/ArchiveReplayWindow.tsx`（826行）が読み込み・再生・シーク・同期補正を持つ。コメントは別窓のコメントOverlayに流れる。
- **Overlayは常にクリックが透過する**（`OverlayControlPanel.tsx` の変更理由のコメント）。そのため、押せるボタンは操作窓に置くしかない。
- 再生位置は `requestAnimationFrame` の `tick` で `startedPosition + 経過秒 × 倍率` として求めている。シークは `seek(position)` で、表示の世代（`stageKey`）を作り直す。
- レスの時刻は `replayOffsetSeconds`（放送開始からの相対秒、同期補正を含まない基準値）で持つ。再生位置と比べるときに `syncOffset` を足す（`getArchiveReplayCommentsThroughPosition`）。ある再生位置 `p` で表示が追いついているレスの基準値は `p - syncOffset` になる。
- 同期補正は「コメントを1秒早く/遅く」ボタン（`syncOffset` を ±1 して `seek(position)`）で行う。ほかに「10秒戻す/進める」と、シークバーがある。
- 再生時間（分）の入力（`durationMinutes`、既定30）がタイムラインの長さ `durationSeconds` になる。放送枠の長さとして使える。
- スレは `container.thread.getThread(url)` で取得する。dat直リンク（`/{板}/dat/{キー}.dat`）は `chlib` の `PATTERNS.CH_DAT` で通常のスレとして扱われる。eddibbの取得先は `ThreadParser.getThreadXhrInfo` の既定の分岐で、`/{板}/dat/{キー}.dat` になる。dat落ちしたスレもこの形式でしか開けないが、いまの経路のまま取得できる見込み（段階0で実画面で確認する）。
- 参考にする提案UIは `features/thread/ui/ThreadScrollFloatingActions.tsx` の「自動読み込み」ボタン。条件を満たしたときだけ下端の中央に出る、1回押すだけの丸いボタン。

## 3. 構成

推定は、React・プラットフォーム・ほかの機能に依存しない純粋関数として作る。再生への組み込みだけを既存の操作窓に合わせる。

```
src/features/archive-replay/
  domain/
    cm-estimation/
      types.ts                  入力・特徴・区間・制約・パラメータの型
      post-features.ts          レス本文 → 特徴（手がかり語、アンカー、長さ）
      binning.ts                特徴付きのレス → 5秒ごとの集計
      scoring.ts                集計 → 区間ごとの手がかり（相対的な勢い、語）
      candidates.ts             手がかり → CM候補（開始・終了・確信度・理由）
      adjusting.ts              遅れの補正、長さの制約、重なりの結合
      selection.ts              合計の制約に合わせて候補を選ぶ（段階4）
      total-check.ts            区間の合計と制約の差を求める（検算）
      estimate-cm-segments.ts   上の段をつなぐ入口
      evaluation.ts             正解との比較（境界の誤差、一致率、合計の誤差）
    cm-proposal.ts              再生位置と区間から、出す提案と自動スキップを決める
    sync-anchors.ts             合わせ直した点 → 合計の制約
  browser/
    use-cm-segments.ts          推定・人の修正・提案・合わせ直した点の状態を持つフック
  ui/
    CmSkipProposal.tsx          スキップ提案のフローティングボタン
    CmSkipProposal.css
    CmSegmentPanel.tsx          区間一覧・検算・周辺を見る
    CmSegmentPanel.css
```

### 依存の向き

- `cm-estimation/` は、自分の中のファイルしか import しない。`CommentCandidate` にも依存させず、入力は独自の最小の型にする。将来 `packages/` へ切り出したり、MCPなどほかの経路から使ったりするときに、そのまま移せるようにするため。
- `sync-anchors.ts` は `cm-estimation/types.ts` の制約の型だけを使う。
- 操作窓 → `use-cm-segments` → `domain/cm-proposal`・`domain/sync-anchors`・`domain/cm-estimation` の一方向にする。
- ほかの機能から使わないので、`FEATURE_PUBLIC_MODULES` は変えない。`domain/index.ts` に再エクスポートも足さず、ファイルを直接 import する。

### 型（案）

```ts
/** 推定の入力。タイムラインからの変換は呼ぶ側で行う。 */
interface CmEstimationInput {
  durationSeconds: number;
  posts: readonly CmPostFeatures[];
  /** CMの合計がわかっている範囲。配信版の長さや、合わせ直した点から作る（§4.3）。 */
  constraints: readonly CmTotalConstraint[];
}

/** 本文そのものは持たず、推定に使う特徴だけを持つ。正解データにもこの形で保存する（§7）。 */
interface CmPostFeatures {
  offsetSeconds: number; // 同期補正を含まない基準値
  cues: readonly CmCue[]; // "cm" | "sponsor" | "return" | "part" | "op-ed" ...
  hasAnchor: boolean;
  length: number;
}

/** 基準値の範囲 [fromSeconds, toSeconds) に含まれるCMの合計。 */
interface CmTotalConstraint {
  fromSeconds: number;
  toSeconds: number;
  totalCmSeconds: number;
  toleranceSeconds: number;
  source: "stream-length" | "sync-anchors";
}

type CmSegmentStatus = "candidate" | "approved" | "rejected";

interface CmSegment {
  id: string;
  startSeconds: number; // 基準値。再生位置と比べるときに syncOffset を足す
  endSeconds: number;
  confidence: number; // 0〜1
  reasons: readonly CmReason[]; // "cue-cm" | "cue-sponsor" | "activity-drop" | "return-burst" | "manual" ...
  status: CmSegmentStatus;
}

interface CmTotalCheck {
  constraint: CmTotalConstraint;
  segmentTotalSeconds: number; // 承認・候補の区間が範囲に含まれる秒数（却下は除く）
  differenceSeconds: number; // 正なら除きすぎ、負なら除き足りない疑い
}

interface CmEstimationParams {
  binSeconds: number;
  baselineWindowSeconds: number;
  minSegmentSeconds: number;
  maxSegmentSeconds: number;
  startLeadSeconds: number;
  endLeadSeconds: number;
  proposalMinConfidence: number;
  // 重みなどは段階1で決める
}
```

- 本文から特徴を作る段（`post-features.ts`）と、特徴から区間を推定する段を分ける。こうすると、正解データに本文を入れずに済む（§7）。
- 閾値と重みはすべて `CmEstimationParams` に集め、既定値は `DEFAULT_CM_ESTIMATION_PARAMS` に置く。関数の中に数値を直接書かない。段階4の調整は、この引数を変えるだけで行う。
- 各段は `(入力, params) => 出力` の形にそろえる。`Date.now()` と乱数は使わない。
- 区間には理由を持たせる。提案のボタンに出して「なぜCMと判定したか」を利用者が判断できるようにするためと、テストで判定の根拠を確かめるため。

## 4. 推定の方式（基準版）

過去ログなので、読み込んだ時点でログ全体がそろっている。そのため、**ある時刻より後のレスも使って判定してよい**（本編に戻ったときの反応の集中など）。推定は読み込み時に行い、合計の制約が増えたとき（§4.3）だけやり直す。やり直しても、人が承認・却下・修正した区間は変えない。

### 4.1 手がかり

§11 のサンプル解析から、**レスの勢いだけではCMを当てられない**とわかった。手がかり語を主に使い、勢いは補助にする。

| 手がかり               | 例                                             | 強さ                           |
| ---------------------- | ---------------------------------------------- | ------------------------------ |
| CMの語                 | 「CM」「ＣＭ」「CM入り」「CMなが」「CMも〜」   | 強い。CMの中か直前を示す       |
| 提供の語               | 「提供」「提供読み」                           | 強い。CMの直前か直後を示す     |
| 構成の語               | 「Aパート」「Bパート」「後半」「アイキャッチ」 | 中くらい。CMの前後を示す       |
| 復帰の語               | 「始まった」「きた」「再開」                   | 弱い。本編中の反応にも出る     |
| 勢いの相対的な落ち込み | 周辺の中央値に比べたレス数の比                 | 弱い。本編の静かな場面でも出る |
| 本編への反応の集中     | 短い同じ言葉が数秒に集まる（例: 台詞の復唱）   | 本編であることを示す           |
| アンカーの割合         | `>>` 付きのレスの割合が上がる                  | 弱い。CM中は雑談が増える       |

語の辞書は `post-features.ts` に置き、全角・半角と大文字・小文字をそろえてから照合する。「CM」は「CMなし」「CM明け」のように本編への復帰を示すこともあるので、前後の語で分ける（段階1のテストで固定する）。

### 4.2 候補の作り方

1. レスを5秒ごとに集計する。各区間で、件数、手がかり語の件数、アンカーの割合を出す。
2. 勢いは、前後120秒の中央値に対する比で見る。スレの盛り上がり方の違いを吸収するため。
3. CMの語・提供の語が集まった区間を、候補の「芯」にする。勢いの落ち込みだけの候補も作るが、確信度は低くする。
4. 芯から前後へ広げて、開始と終了を決める。
   - 開始: 芯の手がかりは実際のCM開始より遅れて書かれるので、手がかりの最初の時刻から `startLeadSeconds` だけ前にする。
   - 終了: 芯の後で、本編への反応の集中か勢いの回復が見えた時刻から `endLeadSeconds` だけ前にする。
5. 長さを `minSegmentSeconds`〜`maxSegmentSeconds`（初期値15〜240秒）に制限し、重なる候補を結合する。
6. 確信度は、理由ごとの重みの和を0〜1に収めたものにする。`proposalMinConfidence` 未満の候補は提案しない（区間の一覧には残す）。

初期値は仮の値で、段階4で正解データに合わせて調整する。CM枠の長さは15秒の倍数になりやすいので、長さの事前分布として使えるかも段階4で確かめる。

### 4.3 CMの合計の制約

区間ごとの正解はわからなくても、**ある範囲に含まれるCMの合計**はわかることがある。手がかり語が少ないスレでは、これが一番の支えになる。合計がわかる場面は2つあり、どちらも `CmTotalConstraint` の同じ形で扱う。

#### 配信版の長さ（`source: "stream-length"`）

- CMの操作パネルに「放送の長さ」と「配信版の長さ」の入力欄を置く。放送の長さの既定値は `durationSeconds`（再生時間の入力）にする。配信版の長さは任意で、空なら制約を作らない。
- 制約は `[0, 放送の長さ)` の範囲で、`totalCmSeconds = 放送の長さ − 配信版の長さ` とする。
- 配信版には、提供の表示や次回予告の有無などで放送と違うところがある。そのため許容幅 `toleranceSeconds` を持たせる（初期値30秒、段階4で調整）。
- 入力欄は `MM:SS` と `H:MM:SS` を受け付ける。区切りのない数字は、下2桁を秒とみなす（`5847` は58分47秒）。解釈した結果を入力欄の横に出し、読み違いに気づけるようにする。

#### 合わせ直した点（`source: "sync-anchors"`、段階3）

配信版を見ながら同期を合わせ直したとき、動画より実況が遅れていた分は、それまでに過ぎたCMの合計に当たる。合わせ直した2点があれば、その間のCMの合計がわかる。利用者が普段している操作からデータが集まるので、記録モード（§7.1）より手間がかからない。

- 操作窓は、シークを除いて再生した秒数 `playedSeconds` を数える（`tick` で進めた分だけ足し、`seek` では変えない）。動画を実況と一緒に止めたり動かしたりしている限り、これが動画の再生位置に当たる。
- 「合わせ直した点」は、利用者が「いま動画と合っている」と示した時点にする。具体的には、「コメントを1秒早く/遅く」を押してから一定時間（初期値5秒）ほかの補正がなかったとき、または「ここで合っている」ボタンを押したとき。1秒の補正を何回か続けて押すことが多いので、押し終わるのを待つ。「10秒戻す/進める」とシークバーは、本編の見返しにも使うので点にしない。
- 点には `(基準値 = 再生位置 − syncOffset, playedSeconds)` を記録する。
- 隣り合う2点 `a`・`b` から、`[a.基準値, b.基準値)` の範囲で `totalCmSeconds = (b.基準値 − a.基準値) − (b.playedSeconds − a.playedSeconds)` の制約を作る（`domain/sync-anchors.ts`）。値が負になったり範囲の長さを超えたりした場合は、操作の誤りとして捨て、ログに残す。
- 許容幅は、反応の遅れと1秒単位の補正を見込んで初期値10秒にする（段階4で調整）。
- 動画が実況と別に止まっていた場合（実況だけ一時停止した、など）は合わない。再生と停止のたびに点の列を区切り、区切りをまたぐ制約は作らない。

#### 制約の使い方

- **検算**（段階1・2）: `total-check.ts` で、制約ごとに区間の合計との差を出し、パネルに表示する。差が正なら除きすぎ、負なら除き足りない疑いがある。差が許容幅を超えた範囲は、パネルで目立たせる。
- **選択**（段階4）: `selection.ts` で、制約の範囲ごとに、確信度の高い候補から合計が `totalCmSeconds` に近づくように選ぶ。候補は1番組で数十件なので、5秒単位の動的計画法で十分に解ける。選ばれなかった候補は確信度を下げ、提案しない。
- **HSMM**（段階6）: 本編とCMの2状態のモデルで、範囲ごとのCMの合計を制約に入れる。

## 5. スキップの提案と承認

### 5.1 提案のフローティングボタン

`ThreadScrollFloatingActions` の「自動読み込み」ボタンと同じ考え方にする。条件を満たした間だけ出し、1回押せば済み、押さなくても再生は止めない。

```
┌───────────────────────────────────────────────┐
│  CMかも（残り 1:24）  [CMをスキップ]  [違う]  [×] │
└───────────────────────────────────────────────┘
```

- 置き場所: 操作窓の下端中央に固定する。Overlayはクリックが透過するため置けない（§2）。
- 出す条件: 状態が `candidate` で確信度が `proposalMinConfidence` 以上、かつ再生位置が `startSeconds + syncOffset` 以上、`endSeconds + syncOffset - 5秒` 未満のとき。残りが5秒を切ったら、飛ばす意味が薄いので消す。
- 「CMをスキップ」: 区間を `approved` にして、`seek(endSeconds + syncOffset)` を呼ぶ。シーク自体は既存の処理に任せる。
- 「違う」: 区間を `rejected` にする。検算でも合計に入れない。
- 閉じる（×）: 状態は変えず、その区間ではもう出さない。区間より前へシークしてから再び入ったときは、もう一度出す。
- 文言: 「CMかも」と残り時間を出す。理由（「CMの語」「提供の語」など）は `title` に出す。
- 見た目: 操作窓のCSSに専用のクラスを作る。色・余白・角丸・影は `tokens.css` と `themes.css` の `--sys-*` を使う。足りない意味トークンはトークン側へ足す。

### 5.2 承認した区間の自動スキップ

提案のボタンだけだと、CMのたびに押す必要がある（1時間ドラマなら6〜8回）。そこで、利用者が承認した区間は、再生位置が入ったときに自動で飛ばす。

- `approved` の区間に再生位置が入ったら、`seek(endSeconds + syncOffset)` を呼ぶ。区間の途中へ手でシークした場合も同じ。
- パネルに「候補をすべて承認」ボタンを置く。提案の条件を満たす `candidate` を、まとめて `approved` にする。検算の差を見てから押せるように、ボタンの近くに検算を出す。
- 自動で飛ばしたことは操作窓に短く表示し、「戻す」で区間の開始へ戻れるようにする（戻したら、その区間は `candidate` に戻す）。
- 判定は `domain/cm-proposal.ts` の純粋関数に置く（`resolveCmPlayback({ position, previousPosition, syncOffset, segments, dismissed })` が「提案を出す区間」と「飛ばす先」を返す）。操作窓には表示と `seek` の呼び出しだけを足す。操作窓をこれ以上大きくしないため。

### 5.3 シークバーと検算の表示

- シークバーに区間を重ねて描く。`candidate` は薄く、`approved` は濃く描き、`rejected` は描かない。どのあたりが飛ぶのかを押す前に見られるようにするため。
- パネルに検算（§4.3）を出す。例: 「区間合計 7:41 ／ 期待値 8:08 ／ 差 −0:27（除き足りない疑い）」。合わせ直した点の制約は、範囲ごとに並べる。

## 6. 人の修正

推定は外れることがある前提で、人が直せるようにする。直した結果は段階4の正解データにもなる。

- 区間一覧（`CmSegmentPanel`）で、各区間の開始・終了を秒単位の入力と「現在位置にする」ボタンで直せるようにする。区間の削除と、手で足すこともできるようにする。手で足した区間の理由は `manual`、状態は `approved` にする。
- **周辺を見る**: 区間の開始・終了それぞれについて、前後30秒のレスを時刻つきで一覧にする。手がかり語には印を付け、勢いを小さな棒グラフで添える。一覧のレスを押すと、その時刻を境界にできる。反応は実際の境界より遅れて書かれるので、境界を秒単位で詰めるときの判断材料にする。一覧の本文は既存の `timeline.comments` から引き、推定の側（特徴だけ）には本文を持たせない。
- 修正は推定結果に重ねて持つ（推定をやり直しても、修正は残す）。
- 保存は段階5で行う。保存の鍵は「正規化したスレURLの組と開始時刻」にする。区間、合わせ直した点、配信版の長さを一緒に保存する。保存先は、既存の設定・IndexedDBの使い方を段階5で確認してから決める。

## 7. 正解データと評価

正解がないと、方式や閾値を変えて良くなったのか悪くなったのか判断できない。推定より先に、正解を作れるようにする。

### 7.1 記録モードと合わせ直した点（段階3）

正解データは2種類の方法で集める。

- **合わせ直した点**（§4.3）: 普段の視聴で、配信版に合わせて同期を直すだけで集まる。区間ごとの正解にはならないが、範囲ごとのCMの合計の正解になる。
- **記録モード**: 動画と合わせて再生しながら、「ここからCM」「ここまでCM」を押して区間を記録する。配信版で見る場合は、実況がCMの話を始めたのに動画が続いているところが「ここからCM」、実況が本編に反応し直したところが「ここまでCM」になる。

どちらも基準値（`syncOffset` を引いた値）で持つ。推定結果と同じ時間の基準にそろえるため。記録は、推定の特徴と合わせてJSONに書き出せるようにする。

### 7.2 正解データの置き方

- リポジトリには、**本文を入れず、`CmPostFeatures` の配列と正解（区間または合計の制約）だけ**を `src/features/archive-replay/domain/cm-estimation/fixtures/` に置く。実在のスレを特定できるURLとスレタイも入れない。
- 元のdatはリポジトリの外に置き、特徴へ変換するスクリプトで作り直せるようにする。手がかり語の辞書を変えたら、変換し直す。
- 番組の種類を散らして集める。30分アニメ、1時間ドラマ、スポーツ中継、レスの少ない深夜番組など。

### 7.3 評価

`evaluation.ts` に、推定と正解を比べる関数を置く。

- 区間の一致: 正解の区間ごとに、IoU（重なりの割合）が0.5以上の推定があれば当たりとする。そこから適合率と再現率を出す。
- 境界の誤差: 当たった区間の開始・終了の誤差（秒）の平均と最大。
- 本編を飛ばす誤り: 正解がCMでない時間のうち、提案した区間に含まれる秒数。これが一番困る誤りなので、別に数える。
- 合計の誤差: 合計の正解（配信版の長さ・合わせ直した点）がある範囲ごとに、推定した区間の合計との差。区間ごとの正解がない番組でも測れるので、正解データが少ない段階4の初めから、方式の比較に使える。

合計の誤差だけで評価すると、「合計は合っているが位置が違う」推定を見逃す。区間ごとの正解がある番組では、区間の一致と境界の誤差も必ず見る。

閾値の総当たり調整はテストの中ではなく、`evaluation.ts` を使う別のスクリプトで行う。テストでは、正解データで指標が決めた値を下回らないことだけを確かめる（回帰を防ぐため）。

## 10. 未決事項・リスク

- **手がかり語がないスレ**: レスが少ない番組や、CMの話をしない番組では、勢いの手がかりしか残らない。合計の制約があればそれで補い、なければ確信度を下げて提案しない、という扱いで足りるかは段階4で確かめる。
- **CM中の盛り上がり**: OPやCMの内容への反応で、CM中のほうがレスが多いことがある（§11）。勢いの重みを大きくしすぎない。
- **配信版と放送の違い**: 配信版で提供の表示や次回予告が削られていたり、逆に配信限定の場面があったりすると、長さの差がCMの合計とずれる。許容幅でどこまで吸収できるかは段階4で確かめる。
- **合わせ直した点の誤り**: 合っていないのに補正を止めた場合や、動画だけを止めた場合は、誤った制約になる。範囲を超える値は捨てるが、もっともらしい誤りは捨てられない。点の一覧をパネルに出して、利用者が消せるようにするかは段階3で決める。
- **自動スキップの誤り**: 承認した区間が間違っていると、本編を飛ばす。「戻す」で取り返せるようにしたが、「候補をすべて承認」は検算の差が大きいときに確認を挟むかを段階2で決める。
- **番組の構成の知識**: 30分アニメの「アバン → OP → Aパート → CM → Bパート → ED」のような並びを、事前分布として使うと精度が上がる見込みがある。ただしサンプルでは提供読みが15分過ぎにあり、番組ごとの差が大きい。段階6のHSMMで、構成の知識をどこまで入れるかを決める。
- **複数スレの合算**: 同じ時間帯の別の板の実況スレも合算すると、レスが少ない問題が和らぐ。いまの読み込みは複数URLに対応しているので、入力側の工夫で済む見込み。
- **操作窓を見ていないとき**: 動画を見ている間は操作窓が見えないことが多い。Overlayに押せない表示で知らせる、全体のショートカットで押せるようにする、などは段階2の実画面の確認の後で決める。承認した区間の自動スキップで、押す回数そのものはかなり減る。
- **今後の候補**: CM中だけ倍速で流す方式、勢いのヒストグラムの表示。どちらも段階4で誤りの量がわかってから考える。

## 11. 段階0の結果（サンプル解析、2026-11-01）

対象: 地上波の30分アニメ（初回放送）の実況4スレ。dat直リンクで取得し、リポジトリの外に置いた。

- レス数: 4スレ合計で3617件。放送枠の30分（23:00〜23:30）のほぼ全体を覆う。スレの切り替わりは数十秒重なる。
- 時刻: 3612件にミリ秒まであり、5秒ごとの集計に十分な細かさがある。
- 勢い: 本編中は10秒あたり15〜50件程度。
- CMの語・提供の語: 全体で5件ほどしかない。手がかり語だけに頼ると見落とす区間が出る。

勢いの落ち込みとCMの関係で、次の2つの反例が見つかった。基準版の設計（§4.1）はこれを前提にしている。

1. **勢いが落ちたのにCMではない**: 23:10:10〜23:10:50 は10秒あたり3〜7件まで落ちた。しかし本文は本編の会話への感想で、23:10:50 に台詞を復唱するレスが一斉に来ていた。本編の静かな場面だった。
2. **CMなのに勢いが落ちない**: 23:16〜23:17 は「提供ここで流すのかよ」「CMも〜」とCMを示すレスがあり、その前後はOPの曲への反応だった。この時間帯は10秒あたり40〜50件と、むしろ多い。

正解（実際のCM区間）はまだわからない。段階3の記録モードで、このサンプルの正解も作る。

## 12. 参考: 公開されたスクリーンショットから得た考え方

別の実況リプレイ機能の作者が、掲示板で仕組みの一部を説明し、画面のスクリーンショットを公開していた。配布物は解析せず、説明と画面から読み取れる考え方だけを参考にした。

- **CMの合計で検算する**: 「配信版の長さ」を入力させ、放送の長さとの差を期待値として、区間の合計との差を表示していた。差が正なら除きすぎ、負なら除き足りない疑い、という読み方も示していた。§4.3 の配信版の長さの制約はここから得た。合わせ直した点から範囲ごとの合計を作り、推定の選択にも使うのは、この計画で足した工夫。
- **境界は人が秒単位で詰める**: 区間ごとに開始・終了の入力と「周辺を見る」があり、反応が境界より遅れることを画面で注意していた。§6 の周辺を見る一覧はここから得た。
- **区間をまとめて除いて再生する**: 選んだ区間を除いて再生する操作があった。この計画では提案を基本にし、承認した区間だけを自動で飛ばす形（§5.2）にした。
- 推定には、作者によるとルール（5秒ごとの集計、15秒の窓、長さ15〜240秒、開始は兆候の15秒前・終了は本編への反応の5秒前）と、LLMにログ本文を渡す方式の両方があった。ルールの閾値は実際の番組との照合で決めたもので、論文はCM中にも直前の場面への投稿が増えることの根拠として使っただけ、とのこと。この計画ではLLMの方式は採らない（§1）。
