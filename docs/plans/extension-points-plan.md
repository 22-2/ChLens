# 拡張ポイント（登録制）の整備計画

## 1. 目的と範囲

コマンド、タブに表示するページの種別、サイドパネルのビュー、ステータスバーの項目、右クリックメニュー、キー割り当てについて、各機能が必要なものを登録できるようにする。Obsidian のように、機能を書く人が用途ごとの入口を見つけやすく、少ない記述で使える API を目指す。

将来のプラグイン API を検討するための下地とするが、本計画では外部に API を公開しない（段階0）。まず内部の機能で使い、実例に合わせて形を調整する。

- 利用者から見た動作は変えない。表示順、ラベル、`when` による出し分け、無効化の条件を保つ。
- 各機能の定義を、その機能のディレクトリへ移す。組み立て層は各機能の登録関数を呼び、個々の定義を直接並べない。
- すべての差し込み口を同じ仕組みに揃えることを目的にしない。使い方が異なるものは別の API にしてよい。
- ユーザースクリプトの読み込み、権限、manifest、外部 API の互換性保証は範囲外とする（段階1以降で別に計画する）。

## 2. 現状（2026-10-27 時点）

| 差し込み口 | 実装 | 状況 |
|---|---|---|
| ステータスバー | `src/view/browser/components/StatusBar.tsx` の `StatusBarProvider` / `StatusBarItem` | 表示の仕組みは登録制。各項目はマウント中だけ `StatusBarItem` で登録し、内容は portal で置き場へ描画する。一方、どの項目を置くかは `App.tsx` のペインが機能のコンポーネント（約9件）を直接並べ、並び順は `components/status-bar-priority.ts` が機能名ごとに一元管理している |
| コマンド | `src/view/browser/commands/browser-commands.ts` と `src/features/*/browser/register-*-commands.ts` | `CommandRegistry` に core と機能側のコマンドを登録する。メディア、お気に入り、自動更新、次スレ、過去実況再生は機能側へ移行済み。フィルターとコメント実況は画面イベント経由のため PR7 で扱う |
| ページ種別 | `src/view/browser/types.ts` の `Page`（10種類の閉じた union） | アイコン、更新・絞り込み可否、自動更新対象、同一性、URL表示、履歴階層、描画キーを `src/view/browser/page-type-definitions.ts` に集約し、描画先は組み立て層の `shell/page-renderers.tsx` に置く。層の依存関係に合わせてメタデータと描画先は別モジュールにし、`TabView` の描画分岐をなくした |
| タブ・ペインの操作 | `state/tabs/use-tab-store.tsx` と `tabActions` | 機能はコマンドのコンテキストから `dispatch` を受け取り、`tabActions.navigate` などを直接送っている |
| サイドパネル | `src/view/browser/shell/SidePanel.tsx` の `views`（6件） | 静的なオブジェクト。ビュー ID は `state/tabs/side-panel-state.ts` の `SIDE_PANEL_VIEWS` で固定し、保存済みの並び順の正規化にも使う |
| 右クリックメニュー | `create*MenuItems` 系の関数と各画面の直書き（約40ファイル） | 画面ごとにばらばら。コマンドと同じ操作を別に組み立てている箇所がある |

コマンドの一部（コメント実況の流れ表示、フィルタの切り替え）は、`commands/` から機能を import できないため `CustomEvent` を経由して機能側へ伝えている。定義を機能側へ移しても、画面が持つ状態を操作するには、対象の窓・タブ・ペインへの経路が別途必要になる。

## 3. 設計方針

### 3.1 機能側から使う入口

機能側には `addCommand`、`registerView`、メニューへの項目追加など、用途が分かる入口を用意する。以下は目指す使用感の例であり、型名・引数・メソッドを確定するものではない。

```tsx
function registerBookmarkFeature(api: ExtensionApi): void {
  api.addCommand({
    id: "page.toggle-bookmark",
    label: "お気に入りを切り替え",
    // 実際のコンテキストと実行処理は既存のコマンドに合わせる。
    run: toggleBookmark,
  });

  api.registerView({
    id: "favorites",
    label: "お気に入り",
    render: () => <SidePanelFavorites />,
  });
}
```

- コマンドの `when`・`isEnabled`・`run` は分けたままにし、非表示と無効表示を区別する。動的なラベルなど既存の定義も維持する。Obsidian の `callback` / `checkCallback` / `editorCallback` のように、同じ目的の書き方を複数並べない。
- メニューは静的な一覧として登録せず、Obsidian の `workspace.on("file-menu", (menu, file) => ...)` と同じく、**メニューを開くたびに呼ばれる関数**を登録する形を第一候補とする。開いた時点の対象と画面の状態を受け取れるため、動的なラベル・区切り線・クリック位置による並び替え・画面固有の処理を扱いやすい。項目からはコマンドの実行も画面固有の処理も呼べるようにする。

  ```ts
  api.onMenu("thread/context", (menu, context) => {
    menu.addItem({ label: "お気に入りに追加", onSelect: () => ... });
  });
  ```

- `ExtensionApi` には `container` やタブストアをまるごと渡さず、機能が使ってよいサービスと操作だけを明示して出す。Obsidian では `app` から内部がほぼすべて見えるため、非公開の API に頼るプラグインが増えた。段階0でも入口を絞っておき、段階1で外部へ公開する範囲を選びやすくする。
- 定義の保持に共通のレジストリが役立つ場合は内部で使う。機能側に汎用レジストリの操作を強制せず、ビューやメニューも同じ実装に揃えることを前提にしない。
- ビューとメニューの API は、コマンドの移行結果と既存の使い方を踏まえて具体化する。段階0で外部向けの互換性は約束しない。

### 3.2 登録・解除と起動順

- **import しただけで登録される作りにしない。** 各機能は登録関数を公開し、組み立て層が初期化時に呼ぶ。登録関数は必要に応じて `vite.config.ts` の `FEATURE_PUBLIC_MODULES` に追加する。
- 登録物の所有者は Obsidian の `Component`（`Plugin` の基底）と同じ考え方にする。`ExtensionApi` は機能ごとに1つ作り、その API で登録したもの（コマンド、ページ種別、ビュー、ステータスバーの項目、メニューの関数、イベントの購読）はすべてその機能が所有する。機能の終了時やテストの後に、所有者を解除すればまとめて消える。
  - 任意の後片付けは `api.register(() => void)` で同じ所有者にまとめる。
  - 各登録は `Disposable` を返すが、機能側は通常それを保持しなくてよい。保持しなくても所有者の解除で漏れなく消える。
  - 段階0で動的な有効化・無効化の UI は作らない。
- 同じ ID の二重登録は、ID と登録元をログに出して後の登録を拒否する。拒否された登録の解除は、先に登録された項目を削除しない。解除の繰り返しも安全に扱う。
- 定義をいつ生成・登録し、どの画面や別窓で共有し、いつ解除するかを差し込み口ごとに決める。少なくとも必要な登録を、対応する利用やセッション復元より前に完了させる。React の再描画や再マウントで重複登録しないようにする。
- 表示順は各差し込み口の要件に従って決定し、同順位の扱いも明確にする。既存の順序は移行時に再現する。共通のレジストリを使う場合も、並び順を用途ごとに指定できるようにする。
- React が変更を購読する必要がある場合は `useSyncExternalStore` を使う。スナップショットは変更がない間は同じ参照を返す。テストでは必要な機能だけを登録した独立した状態を使う。

### 3.3 コマンド ID

- 既存のコマンド ID は変えてよい。コマンドパレットの最近使った履歴（`command_palette_recent_command_ids`）は ID で保存しているため、変えた ID の履歴は移行時に消えることを許容する。
- ID は登録元の機能が分かる形に揃える。登録 API が機能の ID を自動で前に付けるか、定義側で書くかは P0 で決める。
- `navigation.open-url:<URL>` や `page.jump-to-response:<番号>` のように、`:` はすでに動的な引数の区切りとして使っている。機能 ID との区切りに `:` を使う場合は、引数の表し方と衝突しないように決める。
- 履歴に残った旧 ID や未登録の ID は、パレットの表示でエラーにせず無視する。

### 3.4 ページ種別とワークスペース

Obsidian の画面構造と今のコードは、次のように対応する。

| Obsidian | このアプリ | 備考 |
|---|---|---|
| `Workspace` | タブストア（`use-tab-store`）と別窓 | 画面全体の構造 |
| Pane（`WorkspaceSplit`） | `Pane`（横並びのカラム） | 横並びと別窓で足りるため、自由な分割ツリーは作らない |
| `WorkspaceLeaf` | `Tab` | 履歴・ピン留めを持つ入れ物 |
| `View` | `Page`（`type` とパラメータ） | タブの中身 |
| `getState` / `setState` | `Page` の各項目と `TabViewState` | セッションに保存・復元する状態 |
| `getEphemeralState` | スクロール位置などの一時状態 | |

Obsidian では `registerView(type, creator)` で登録した View 自身が、アイコン・表示名・状態を知っている。同じく、ページ種別ごとの知識を1つの定義にまとめる。PR5 で、次の形にした。

```tsx
// src/view/browser/page-type-definitions.ts（UI 部品層）
export const PAGE_TYPE_DEFINITIONS: { [T in PageType]: PageTypeDefinition<PageOfType<T>> } = {
  thread: {
    icon: MessageSquareText,
    refreshable: true,
    filterable: true,
    autoRefreshable: true,
    getLocation: (page) => page.threadUrl, // page はスレのページに絞り込まれる
    buildHierarchy: (page) => [...],
  },
  settings: { icon: Settings, refreshable: false, filterable: false, autoRefreshable: false, displayLabel: "設定" },
  // ...
};

// src/view/browser/shell/page-renderers.tsx（組み立て層）
const PAGE_RENDERERS: { [T in PageType]: (page: PageOfType<T>, context: PageRenderContext) => ReactNode } = {
  thread: (page, context) => <ThreadPage page={page} ... />,
  // ...
};
```

- 定義（メタデータ）と描画先は別のモジュールに置く。描画先はページのコンポーネントを import するため組み立て層に置き、定義は UI 部品層に置いて、層の依存ルールを保つ。
- 定義は種別ごとに型を絞った関数で書く。URL で区別する種別は `getLocation` を持ち、同一性・表示状態のキー・描画キー・表示 URL はすべてここから求める。種別ごとに「どの URL を使うか」を文字列で別々に書く形は、組み合わせの誤りを型で検出できず、別の板やスレが同じページとして扱われる誤りを黙って生むため採らない。
- `TabView`、`PageTypeIcon`、同一ページの判定、再取得・絞り込みの可否などは、この定義を引くだけにする。コマンドの `when` にある `page.type === ...` の判定も、できるものは定義の項目で表す。
- 全種別の出力（同一性・表示状態のキー・描画キー・表示 URL・階層・各可否）は `page-type-definitions.test.ts` で固定している。定義の書き方を変えるときは、このテストが変わらないことを確かめる。
- `Page` はセッションに保存される形でもある。段階0では `Page` 型と保存形式を変えず、種別ごとの知識の置き場所だけを移す。未登録の種別が保存値に含まれていても、復元で失わず、画面が壊れないようにする。
- 型の安全性を保つため、段階0では `Page` の union と `PageType` を残し、定義が全種別を網羅していることを型で検査する。外部から新しい種別を追加できるようにするかは段階1で決める。
- Obsidian のように `View` クラスを継承して `containerEl` を直接操作する形にはしない。React コンポーネントを返す対応表にする。
- 名前の衝突を避ける。Obsidian の「View」はタブの中身を指すが、このアプリではタブの中身を「ページ」、サイドパネルの中身を「ビュー」と呼び分け、API も `registerPageType` と `addSidePanelView` のように分ける。

ワークスペースの操作は、機能に `dispatch` を渡す代わりに、Obsidian の `Workspace` に当たる窓口から行う。

```ts
api.workspace.openPage(page, { newTab: true });
api.workspace.getActiveTab();
api.workspace.on("active-page-change", (page) => ...);
```

- 窓口は実行元の窓・ペインに結び付け、別窓や2ペインで別の対象を操作しないようにする（3.6）。
- この窓口が、3.7 で後回しにしている狭いコマンドコンテキストの土台になる。段階0では既存の `dispatch` 経由の処理と併用してよく、移した機能から順に置き換える。

### 3.5 ステータスバー

表示の仕組み（`StatusBarProvider` / `StatusBarItem` / portal による描画）は変えない。portal 方式は Preact で古い VNode ツリーが解放されずメモリが増え続けた問題への対策であり、登録 API のために JSX を保持する形へ戻さない。

変えるのは「どの項目を、どの順で置くか」の決め方である。サイドパネルのビューと同じく、機能が React コンポーネントと配置情報を定義として登録し、各ペインがそれを描画する。

```tsx
api.addStatusBarItem({
  id: "ng",
  alignment: "left",
  priority: 5,
  component: NgStatusItem,
});
```

- 定義はアプリで共有し、描画はペインごとに行う。項目のコンポーネントはペインのプロバイダの中で描画されるため、今と同じくペイン単位の状態（NG、書き込みパネル、自動スクロールなど）をフックで使える。
- `CommentOverlayStatusItem` の `isActive` のように、ペインから受け取る値はコンポーネントの props の決まった形（ペイン ID、アクティブかどうかなど）で渡す。
- `alignment` と `priority` は定義側に持たせ、`status-bar-priority.ts` が機能名を知らない形にする。既存の並び順は移行時に再現する。
- `StatusBarMode`（自動更新中のバー全体の見た目）は項目のコンポーネントの中で使い続けてよい。
- Obsidian の `addStatusBarItem()` のように DOM 要素を返して命令的に書き換える形にはしない。

### 3.6 層と画面状態の関係

- 登録 API と定義型は UI 部品層に置くため、機能から参照してよい。登録関数を呼ぶのは組み立て層とし、UI 部品層から機能を import しない今のルールを保つ。
- コマンドは実行元の窓と対象のタブ・ペインを操作する。定義の登録とは別に、画面固有の状態やハンドラーをどう取得し、画面終了時にどう解除するかを設計する。別窓や2ペインで別の対象を操作しないことを確認する。
- 既存の `CustomEvent` は、対象を正しく扱える直接呼び出しの経路ができるまで維持してよい。定義の移動だけでイベントを削除せず、置き換え後に不要になったものを削除する。

### 3.7 コマンドのコンテキスト

`BrowserCommandContext` は `dispatch` などの内部状態をそのまま渡していて大きい。段階0では既存の形を使ってよい。外部へ公開するときは、内部型をそのまま約束せず、操作可能な対象と機能を絞った別のコンテキストを定義する（段階1で検討）。その中心には 3.4 のワークスペースの窓口を使う。

## 4. 実装順序と完了条件

各段階の具体的な API は、先行段階の結果を踏まえて決める。実装は途中でも既存動作を保てる単位に分け、各単位を個別にレビュー・マージできるようにする。

- [x] **P0. 登録 API と寿命の設計**
  - コマンドの登録・取得・実行・解除と、機能単位の後片付けの使用例を用意する。登録の起動順と所有者を決める。
  - 必要な保持・購読の仕組みを実装し、二重登録、拒否された登録の解除、解除の繰り返し、購読、表示順、変更がないときのスナップショットを確認する。
- [ ] **P1. コマンド**
  - `BROWSER_COMMAND_DEFINITIONS` を登録方式に置き換え、`resolveBrowserCommands` / `executeBrowserCommand` / `getBrowserCommandLabel` の引数と戻り値は変えない。URL 入力やレス番号指定など、通常の定義以外の実行経路も維持する。
  - 最初は全定義をそのまま1つの登録関数から登録し、既存テスト（`browser-commands.test.ts` など）が通ることを確認する。
  - 次に1機能を移して API と対象の扱いを確かめ、その結果を踏まえてほかの機能も移す。候補は自動更新、次スレ、コメント実況、お気に入り、Imgur 画像の削除。
  - `BrowserCommandGroup` は段階0では固定のままとし、登録可能にする必要が生じたら別途検討する。
  - コマンド ID は 3.3 の方針で付け直してよい。付け直す場合は、ID を参照するテストと実行経路をまとめて更新する。
  - 完了条件：コマンドパレットの表示順・ラベル・有効状態・実行対象が移行前と同じ（ID と最近使った履歴は除く）。機能固有の定義と処理を機能側へ移せている。旧 ID の履歴が残っていてもパレットが壊れない。
- [ ] **P2. ページ種別の定義とワークスペースの窓口**
  - 3.4 の方針で、ページ種別ごとの知識（描画、アイコン、同一ページの判定、再取得・絞り込みの可否など）を定義へまとめ、`TabView` や各判定ユーティリティが定義を引く形にする。`Page` 型と保存形式は変えない。
  - 全種別を一度に移してから、各機能に属するページ（スレ、スレ一覧など）の定義を機能側へ移す。
  - `api.workspace` の最小限の操作（ページを開く、アクティブなタブを得る）を用意し、P1 で移したコマンドの一部で使って形を確かめる。
  - 完了条件：全ページの表示・タブのアイコンとタイトル・同一ページの判定・更新ボタンや絞り込みの出し分け・セッション復元が変わらない。ページ種別を足すときに直す場所が定義1か所と型に限られる。
- [ ] **P3. サイドパネルのビュー**
  - コマンドの移行結果を踏まえてビュー登録 API を決め、`ViewDefinition` と機能固有の定義を機能側へ移す。
  - ビューの登録をセッション復元より前に完了する。保存済みの並び順や選択を、未登録の ID が一時的にあるだけで失わないようにし、表示できるビューと保存値を区別する。全件未登録の場合の表示と復元も決める。
  - 完了条件：既存のビューの表示・並べ替え・保存・復元が変わらず、未登録のビューがあっても画面が壊れない。
- [ ] **P4. ステータスバーの項目**
  - P3 と同じ「コンポーネントを登録し、描画する場所が並べる」形で、3.5 の方針に沿って移す。`App.tsx` から機能の項目コンポーネントの直接 import をなくし、並び順を定義側へ移す。
  - 完了条件：1ペイン・2ペイン・別窓で、項目の表示・順序・ペインごとの内容・自動更新中の見た目が変わらない。
- [ ] **P5. 右クリックメニュー**
  - `thread/context` などのメニューに、3.1 の「開くたびに呼ばれる関数」で機能が項目を追加する入口を用意する。コマンド呼び出しに加え、画面固有の処理も扱えるようにする。

## 5. 作業の進め方

4章の P0〜P6 は設計上の段階を表し、本章は PR の単位と作業の確認項目を表す。進捗は PR ごとに本章のチェックを付け、段階の完了条件を満たしたら4章のチェックも付ける。

### 5.1 着手前に決めること

決めたら3章と7章の該当箇所を決定事項として書き換える。

### 5.4 進め方の原則

- 1回の変更では「置き場所や登録方法を変える」ことと、利用者から見える動作の変更を分ける。段階0では既存動作を変えない。
- 移行中は旧一覧と新しい登録方式を併用してよいが、同じ定義を両方に置かない。
- 登録や実行の失敗は握りつぶさず、原因の追跡に必要な情報をログに出す。

### 5.5 実装時の注意点

PR1〜3 の実装と見直しで分かったことと、以降の PR で気を付けることをまとめる。

#### モジュールの使い分け

- `commands/command-definition.ts`：コマンドの型、グループ定義、定義から使う共通処理（`getCommandPageTarget`・`getCommandToast`・`getCommandSurface`・`isCommandConfigSwitchOn`・`toggleCommandConfigSwitch`）。機能の登録関数と登録 API はここだけを参照する。
- `commands/browser-commands.ts`：core のコマンド一覧、`browserCommandRegistry`、`registerCoreCommands`、解決・実行処理。参照するのは組み立て側（`index.tsx`）、コマンドパレット周り、テストに限る。機能から import すると、1000行を超える一覧と、その依存がまとめて入る。
- `extension/`：登録 API とレジストリ。コマンドの具体的な定義や画面の状態を持ち込まない。

#### 定義を移すとき

- 移す処理が `browser-commands.ts` の補助関数を使っている場合、機能側へ複製しない。複数の機能で使うものは `command-definition.ts` へ移し、1つの機能でしか使わないものはその機能へ移す。PR3 では `getCommandPageTarget` と同じ処理を機能側に複製してしまい、見直しで直した。
- 補助関数を呼び出し先の処理で置き換えるときは、中身が同じであることを確かめる。たとえば `openQuickAccessPage` は `tabActions.navigate` を呼ぶだけだったため置き換えられたが、`openSettings` は既存の設定タブを探すため置き換えられない。
- 「変更理由」のコメントは、コードと一緒に移す。
  - `switch` の分岐を対応表にまとめるときは、各 `case` に付いていたコメントを対応表の該当する項目へ移す。PR5 では、クイックアクセスの同一性と新規タブの履歴の理由が消え、見直しで戻した。
  - 移したあと、コメントが説明するコードの直前に残っているかを確かめる。PR4 では関数だけを移し、コメントが無関係な関数の上に残った。
  - コメントには確かめた事実と理由だけを書く。理由が分からないときは推測で補わず、動作だけを書く。
- ロガーのタグは移した先の機能名にする（例：`createLogger("features/media")`）。

#### 表示順と登録の順番

- 機能のコマンドは `beforeCommandId` で core のコマンドを基準に並ぶ。そのため、起動時もテストも core を先に登録する。基準が見つからないと警告ログを出して末尾に並ぶ。
- 他のコマンドの基準になっているコマンドを機能へ移すときは、`beforeCommandId` でその ID を指定している箇所を検索し、登録の順番も見直す。基準が機能どうしで連鎖し始めたら、グループ内の順序を数値（`order`）で持つ方式へ移るかを検討する（7章）。
- 同じ基準の直前に入る機能どうしは、`index.tsx` で登録した順に並ぶ。PR4 で auto-refresh と next-thread がどちらも Zen モードの直前に入り、機能どうしの登録順に依存し始めた。依存する組み合わせを増やしたときは、`index.tsx` のコメントも更新する。

#### 所有者と解除

- 機能の登録関数が受け取るのは `api` だけで、解除はできない。解除は `createExtensionOwner` を呼んだ側（起動処理やテスト）が行う。
- `index.tsx` の所有者はアプリの終了まで残すため解除しない。React のコンポーネントやフックの中で登録しない（再描画や再マウントで二重に登録される）。

#### テスト

- `browserCommandRegistry` はモジュール内で1つだけ持つため、テストどうしで登録が残りやすい。`beforeEach` で所有者を作って登録し、`afterEach` で必ず解除する。解除し忘れると、次のテストの登録が二重登録として拒否され、古い定義のまま実行される。
- コマンドパレットやナビゲーションバーを単体で描画するテストでも、コマンドを明示的に登録する（起動処理を通らないため一覧が空になる）。
- 機能のコマンドのテストでも、表示順を保つため core を先に登録する。
- 既存の判定を書き換える前に、今の出力を表やインラインスナップショットのテストで固定し、そのテストを先に別のコミットにする。書き換えたあともテストが変わらないことで、動作が同じだと示せる。PR5 の見直しでは `page-type-definitions.test.ts` で10種すべての出力を固定してから書き換えた。
- テストの URL は `example.com` などの架空のものにし、正規化の差が出るよう末尾のスラッシュや `http` の有無を混ぜる。

#### PR4 以降で気を付けること

- 移したい処理が画面の状態を必要とするとき、機能の都合で `BrowserCommandContext` に項目を足さない。段階0では既存の項目だけを使い、足りない場合は P2 の `api.workspace` を待つ（PR7 に回す）。
- 新しい `CustomEvent` を足して画面へ届ける形にもしない。既存のイベントを使うコマンドは PR7 でまとめて扱う。
- 機能どうしの import は今までどおり `FEATURE_PUBLIC_MODULES` に従う。登録関数を組み立て側（`index.tsx`）から呼ぶだけなら、一覧へ追加する必要はない。

#### 定義や対応表の書き方

- 種別ごとの違いは、型を絞った関数で書く。`{ [T in PageType]: Definition<PageOfType<T>> }` のような対応表の型を使うと、各関数の引数が種別ごとに絞り込まれ、種別と処理の組み合わせを型で検査できる。
- 「どの値を使うか」を `"thread-url"` のような文字列で書き、別の場所で解釈する形にしない。PR5 では同じ情報を4つの項目に文字列で書いており、組み合わせを誤ると別の板やスレが同じページとして扱われる誤りを、型でも実行時でも検出できなかった。
- 対応表から取り出した関数を呼ぶときの型の変換は1か所にまとめ、変換してよい理由をコメントに書く。実行時に種別を確かめて例外を投げる処理で型を補わない。
- 多くのファイルが import するモジュール（`types.ts` など）から、別のモジュールの関数を再 export しない。再 export すると、型だけを使うファイルにもアイコンなどの依存が入る。呼び出し側の import 先を直接変える。
- 移したあとに中継するだけになったファイルは残さず、呼び出し側を直して削除する。ファイル冒頭の説明が実態と合わなくなるため。

#### 変更の分け方とコミット

- 表示名の変更（PR4 の「類似スレ」から「関連スレ」など）、README、E2E の期待値のように利用者から見える変更は、置き場所の整理とは別の PR にする。同じブランチに入れた場合は、PR の説明で分けて書く。
- 表示名を変えるときは、段階0では ID も合わせて変えてよい（3.3）。「履歴との互換性」を理由に古い名前の ID を残すときは、その ID が本当に今まで使われていたものかを確かめる。PR4 では直前のコミットで ID が既に変わっていた。
- コミットメッセージの本文は、改行を実際の改行で書く。コマンドラインで `\n` と書くと、改行ではなく文字のまま記録される（PR4 の2つのコミット）。複数行の本文は `git commit -F` やエディターで書く。

## 6. 検証

- 各段階で `vp check` と `vp test` を通す。
- コマンドパレット、サイドパネル、移したメニューは、Chrome 版と Tauri 版の実画面で表示順と動作を確認する。別窓と2ペインでも対象が正しいことを確認する。
- ページ種別は、全種別のページを開き、タブのアイコンとタイトル、更新ボタンと絞り込みの出し分け、同じページを開いたときの既存タブへの切り替え、再起動後のセッション復元を確認する。
- サイドパネルは保存済みの並び順と選択の復元、未登録ビューを含む保存値、登録後の再表示を確認する。
- 必要に応じて、移行前後のコマンド一覧（ID・ラベル・グループ・順序）を比較するテストを一時的に置く。

## 7. 判断が必要な点

- 各差し込み口の登録を窓ごとに持つか、共有するか。定義の共有と、窓・タブ・ペインに紐づく実行対象は分けて考える。
- メニューの配置、サブメニュー、チェック状態、動的な一覧を、開くたびに呼ばれる関数の中でどう表すか。既存メニューの移行を通して決める。
- ページ種別を外部から追加できるようにするか（`Page` を開いた union にするか）。段階0では閉じた union のまま進める。
- `api.workspace` にどこまでの操作（ペインの指定、別窓への移動、タブの並べ替えなど）を持たせるか。
- 段階1（ユーザースクリプト）に進むかどうかと、その範囲。Chrome 版は MV3 の制約でリモートコードを実行できないため、Tauri 版限定になる見込み。
